# Discord Activity: Einrichtung und tatsächlicher Prüfstand

Die Activity verwendet dieselbe `WorldPage` und dieselben öffentlichen Weltdaten wie Desktop und Web. Einstieg: `/activity`; außerdem erkennt der gemeinsame Frontend-Einstieg die Discord-SDK-Parameter `frame_id` und `instance_id`, wenn Discord die Anwendung am Root-Pfad startet. Ein Aufruf außerhalb von Discord zeigt eine Erklärung statt einer angeblich angemeldeten Sitzung.

## Externe Einrichtung

1. In derselben Discord-Anwendung Activities aktivieren und die gewünschte Installation im Developer Portal konfigurieren. Für Entwicklung kann die Activity im App Launcher der vorgesehenen Testumgebung gestartet werden. Der offizielle Ablauf einschließlich Entry Point ist in [Discord: erste Activity](https://docs.discord.com/developers/activities/building-an-activity) beschrieben.
2. Das gebaute Frontend (`pnpm --filter @dofus/desktop build`, Ausgabe `apps/desktop/dist`) über einen erreichbaren HTTPS-Host bereitstellen. Der Host muss SPA-Fallback auf `index.html` unterstützen. `/api/*` an das Companion-Backend weiterleiten. Im Development übernimmt die Vite-Konfiguration den `/api`-Proxy zu `127.0.0.1:4310`; dieser Proxy gehört nicht zum statischen Produktionsbuild.
3. Im Developer Portal die URL-Mapping-Wurzel `/` auf diesen HTTPS-Host setzen. Netzwerkzugriffe der Activity benutzen ihre eigene Origin und werden durch den Discord-Proxy vermittelt; siehe [Discord: Networking](https://docs.discord.com/developers/activities/development-guides/networking). Kein Abruf von `localhost` auf dem Rechner eines Teilnehmers ist erforderlich.
4. Ausschließlich serverseitig setzen: `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_TOKEN`. Diese gehören nicht in `VITE_*`, JavaScript-Bundles, Git oder Activity-URLs. Der Client liest nur die öffentliche Client-ID aus `/api/activity/config`. Den vom offiziellen Tutorial vorgesehenen OAuth2-Redirect im Portal eintragen. Der Codeaustausch erfolgt serverseitig.
5. Für den öffentlichen Activity-Betrieb einen eigenen `DATA_DIR` ohne persönliche Desktop-Profile verwenden. Ein zufälliger Companion-Verbindungsschlüssel schützt die privaten REST-Routen weiterhin; dieser Schlüssel wird nie an Activity-Teilnehmer ausgegeben. Im vorgeschalteten Webserver nur erforderliche Activity- und öffentliche Weltdatenrouten freigeben.
6. Das Backend muss die [Discord Activity Instance API](https://github.com/discord/discord-api-docs/blob/main/developers/activities/development-guides/multiplayer-experience.mdx) erreichen können. Mit dem Bot-Token prüft es die zur Anwendung gehörende Instanz und die Mitgliedschaft des angemeldeten Users. Ein vom Browser behaupteter Instanz- oder Benutzername allein genügt nicht.

## Implementierter Ablauf

Beim Aktivieren erzeugt Discord den offiziellen Default-Entry-Point „Launch“ selbst. Die globale Slash-Command-Registrierung erhält bestehende Entry-Point-Kommandos, damit ein erneutes Registrieren der Companion-Befehle den Activity-Einstieg nicht entfernt. `/karte oeffnen` bietet zusätzlich den konfigurierbaren HTTPS-Weblink; es erzeugt keinen erfundenen Discord-Startlink.

Das Embedded App SDK fordert `identify` an. Ein einmaliger fünf Minuten gültiger Challenge wird an die anfragende IP gebunden; ein Code kann mit diesem Challenge nicht erneut eingelöst werden. Nach dem serverseitigen OAuth-Codeaustausch werden Anwendung und Activity-Mitgliedschaft geprüft. Der Client authentifiziert danach das SDK. Das eigene einstündige Sitzungstoken und der OAuth-Zugriffstoken bleiben im Browser-Arbeitsspeicher; die Datenbank speichert ausschließlich den Hash des eigenen Sitzungstokens. Es gibt keine Weitergabe des Companion-Schlüssels.

Teilnehmer derselben Activity teilen ausdrücklich ausgewählte `worldId`, Karten-IDs, Ressourcen-IDs und einen Titel. Andere Felder werden vom Zustandsschema entfernt. Persönliche Marker, Charaktere, Chattexte, Inventare und Builds werden nicht geladen. Der öffentliche Routenrechner ist erreichbar; der auf privaten Ressourcenbeobachtungen basierende Farmrechner wird nicht über die Activity weitergereicht.

Die gemeinsame Sitzung wird alle drei Sekunden aktualisiert; versteckte Tabs pausieren die Abfragen und laden beim Sichtbarwerden erneut. Netzwerkfehler erscheinen mit einem Wiederverbinden-Button. Gleichzeitiges Teilen verwendet `expectedRevision`; ein Konflikt lädt den neuen Zustand und erfordert erneutes ausdrückliches Teilen. Eine Sitzung wird serverseitig spätestens nach 30 Sekunden erneut auf Discord-Mitgliedschaft geprüft.

## Prüfungen und verbleibende Freischaltung

`pnpm exec tsx --test apps/backend/tests/activity.test.ts`: **3/3 lokale Integrationstests erfolgreich**, mit einem ausdrücklich gemockten Discord-Transport. Geprüft wurden Challenge-Wiederverwendung, IP-Bindung, Anwendung und Instanzmitgliedschaft, Tokenhash, OAuth-Ablehnung, getrennte Sitzungen, Revisionskonflikte, abgelaufene/fehlende Tokens, Entfernen privater Zusatzfelder und die nicht vorhandene Farm-Proxyroute. Ein zusätzlicher Test über die vollständige Companion-API bestätigt: ein gültiges Activity-Token erlaubt keinen Zugriff auf private Marker, gespeicherte Routen, Charaktere oder Builds. Die öffentliche Konfiguration enthält keine Secrets. Das bestätigt den lokalen Protokollablauf; es ist kein Discord-Livetest.

HTTPS-Hosting, Developer-Portal-Freischaltung, echte OAuth-Berechtigung und das gemeinsame Öffnen durch zwei Discord-Teilnehmer können ohne die entsprechende externe Umgebung nicht als erfolgreich bestätigt werden. Der abschließende Abnahmetest ist: Activity in Discord öffnen, zwei echte Teilnehmer anmelden, Kartenroute ausdrücklich teilen, Konflikt bei gleichzeitiger Bearbeitung prüfen, Teilnehmer entfernen und Sperrung nach der nächsten Mitgliedschaftsprüfung prüfen. Keine privaten Companion-Daten dürfen im Netzwerkmitschnitt einer Activity erscheinen.
